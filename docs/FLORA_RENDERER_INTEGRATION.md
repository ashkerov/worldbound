# Рендер растительности: контракт данных и план интеграции

**Ветка:** `experiment/unity-flora-renderer` (от `experiment/unity-windows-prototype`, коммит `98994d0`) · **Статус:** модуль и стенд готовы; к настоящему миру **не подключены** · Отчёт — `docs/UNITY_FLORA_RENDERER_REPORT.md`

Документ для разработчика, который будет подключать рендер к настоящей C#-симуляции. Всё, что требует правки общих файлов (`WorldApp.cs`, `SimHost`, `Worldbound.Runtime.asmdef`, `WorldView.cs`), здесь **только описано** — в этой ветке эти файлы не менялись.

---

## 1. Главное правило

Рендер растительности — **не часть симуляции**. Он получает снимки и условия кадра и строит из них картинку:

- не создаёт и не удаляет растения мира, не меняет биомассу, почву, численность видов;
- не вызывает генератор случайных чисел симуляции (вариации — собственный хеш от номера растения);
- камера влияет только на видимость и качество отрисовки, ни на одно экологическое значение;
- климат не считает: время года, ветер, снег приходят извне.

Граница проверяется автоматически (`FloraStandBuilder.RunChecks`): хеш `Simulation.StateHash()` до и после снимка адаптером совпадает; свёртка опубликованного состояния источника до и после работы рендера совпадает.

| `Worldbound.FloraView.SimAdapter` | `Runtime/WorldView/Flora/SimAdapter` | Contract, `Worldbound.Sim` (`noEngineReferences`) | `SimFloraSnapshotSource`: настоящая симуляция → контракт, только чтение |

## 3. Контракт данных

Пространство — мировые метры, начало `(0, 0)` в углу мира, `x` — восток, `z` — север (как `WoodyStore.X/Z`). Сетка — эко-ячейки 8 м, чанк 16 × 16 ячеек = 128 м (как `FLORA_CHUNK_CELLS` TS-протокола). Мир S: 256² ячеек, 16² = 256 чанков; мир M: 512² ячеек, 32² = 1024 чанка.

### 3.1. `FloraGrid`

| Поле | Тип | Значение |
|---|---|---|
| `Cells` | int | ячеек по стороне (`Geo.N`) |
| `CellSize` | float | 8 м (`Geo.CellSize`) |
| `ChunkCells` | int | 16 |
| производные | | `ChunksPerSide`, `ChunkCount`, `ChunkAt(x, z)`, `ChunkOfCell(c)`, `CellOfChunk(k, local)` |

### 3.2. `WoodyPlant` — древесное растение (32 байта, `StructLayout.Sequential`)

| Поле | Тип | Источник в ядре | Примечание |
|---|---|---|---|
| `Id` | uint | `WoodyStore.IdOf(i)` (поколение + индекс) | устойчив, пока растение живо; задаёт вариант модели, поворот и оттенок |
| `X`, `Z` | float | `WoodyStore.X/Z` | м |
| `Height` | float | `FloraMath.WoodyHeight(t, s, b)` | м; адаптер квантует до 5 см |
| `CrownRadius` | float | `FloraMath.CrownRadius(t, s, b)` | м; квант 5 см |
| `Biomass` | float | `WoodyStore.Biomass` | необязательно (0 — нет); адаптер — шаг ≈ 2 % |
| `Species` | ushort | `WoodyStore.Species` | номер вида каталога |
| `Leaf` | byte | `WoodyStore.Leaf` × 255 | облиственность (фенология симуляции); квант 1/32 |
| `Health` | byte | `WoodyStore.Health` × 255 | квант 1/16 |
| `Stage` | byte | `WoodyStore.Stage` | 0 всход, 1 подрост, 2 взрослое, 3 старое; 255 — неизвестно |
| `Flags`, `Reserved` | | | зарезервировано |

Квантование уменьшает «дребезг» чанков: суточный прирост в 1–2 см не делает чанк изменившимся.

### 3.3. `WoodyChunk`

`Chunk` (номер), `Plants[]`, `Count`, `Checksum`. Растения внутри чанка упорядочены по `Id`. Пустой чанк в инкрементальном пакете (`Count = 0`) означает «все растения чанка исчезли».

### 3.4. `FieldChunk` — поля по ячейкам чанка (16² ячеек, строка за строкой по z, затем x; ячейки за краем мира — нули)

| Массив | Байт на ячейку | Содержимое |
|---|---|---|
| `Herbs` | H (= `HerbOrder.Length`, сейчас 8) | плотность каждого вида трав: байт v → (v/255)² · 1020 г/м² (как `HERB_FIELD_MAX` в TS) |
| `HerbCell` | 4 | покрытие травостоем 0..1; высота травостоя, см (0 — «по видам», решает рендер); зелень 0..1 (1 — вегетирует, 0 — сухая/покой); доля ветоши 0..1 |
| `Canopy` | 4 | покрытие кронами деревьев; доля хвойных в нём; покрытие кустарниками; средняя облиственность древесных |
| `Surface` | 2 | снег 0..1; влажность поверхности 0..1 (необязательно: `null` — используется общее значение кадра) |

### 3.5. `FloraUpdate` — пакет изменений

| Поле | Значение |
|---|---|
| `Kind` | `Full` — состояние целиком (отсутствующий чанк пуст); `Incremental` — только чанки, изменившиеся после `BaseVersion` |
| `WorldId` | при смене (новый мир, загрузка сохранения) рендер всё сбрасывает |
| `Version`, `BaseVersion` | версия после применения; для инкремента — версия, к которой он применяется |
| `SimTick` | такт снимка (журнал, отладка) |
| `Grid` | сетка (должна совпадать с сеткой рендера) |
| `Woody[]`, `Fields[]` | чанки |
| `WoodyStateChecksum`, `FieldStateChecksum` | свёртка сумм **всех** чанков мира после применения — проверка целостности |
| `WoodyTotal` | всего древесных |

### 3.6. `FloraEnvironment` — условия кадра (каждый кадр, не версионируется)

| Поле | Источник в ядре |
|---|---|
| `YearPhase` 0..1 (0 — начало весны) | `SimTime.YearFraction(tick, DaysPerSeason)` |
| `DayPhase` 0..1 | `SimTime.DayFraction(tick)` (рендеру флоры не нужна, для освещения) |
| `WindDirection` (рад, куда дует), `WindSpeed` (м/с), `Gustiness` 0..1 | `Weather.WindAt(world, tick, ref wind)` — чистая функция |
| `Snow` 0..1 | общий снег / множитель к полю `Surface` |
| `Wetness` 0..1 | дождь / роса |
| `Dryness` 0..1 | резерв (если поле зелени не передаётся) |

### 3.7. Каталог: `FloraCatalogInfo`

`Species[]` (`Id`, `Key`, `Form`, `Habit`, `MaxHeight`, `MaxCrownRadius`) и `HerbOrder[]` (номера трав в порядке столбцов `Herbs`). Рендер выбирает визуальный профиль **по ключу** (`"birch"`, `"meadow-grass"`…), не по номеру; неизвестный вид получает общий профиль по форме и типу листвы — новый вид каталога не ломает рендер.

## 4. Передача снимков

### 4.1. Схема

```
Simulation (такты)                                  главный поток Unity
   │ после суточного/часового шага флоры
   ▼
SimFloraSnapshotSource.CaptureWoody / CaptureFields(rows) ──► FloraSnapshotPublisher (Stage*, Commit)
                                                                    │ версии по чанкам, суммы
FloraRenderer.Update(cam, dt) ── TryGetUpdate(worldId, version) ◄───┘
   │ Full или Incremental (только чанки новее версии рендера)
   ▼
FloraChunkManager.Begin / Step(budget ms) ── Burst: растения → экземпляры по чанкам
   │ после последнего чанка: свёртка сумм == WoodyStateChecksum? иначе Version = −1 → полный снимок
   ▼
FloraWoodyLayer.Cull (Burst) → RenderMeshIndirect;  FloraGrassRenderer (Burst) → RenderMeshIndirect
```

### 4.2. Издатель версий (`FloraSnapshotPublisher`)

- `StageWoody(chunk)` / `StageField(chunk)` — подготовить новые объекты чанков (контрольная сумма считается здесь). **Опубликованный объект нельзя менять** — новые данные = новый объект; поэтому рендер читает их без копирования и без блокировок на время применения.
- `Commit(tick)` — чанки с той же суммой не считаются изменившимися; изменившимся ставится новая версия.
- `TryGetUpdate(appliedWorldId, appliedVersion, out update)` — `Full`, если мир другой или версия неизвестна; иначе `Incremental` с чанками, версия которых больше применённой; `false` — нового нет. Состояния «на получателя» нет: несколько рендеров (основная камера, мини-карта, окно сравнения) читают одну публикацию.
- Потокобезопасен (внутренняя блокировка): `Stage/Commit` можно вызывать из потока симуляции, когда он появится.

### 4.3. Частота обновлений

| Данные | Когда снимать | Стоимость (замер/оценка) |
|---|---|---|
| Древесные | раз в игровые сутки после пересчёта полога (порция 0 часа 0) — тогда же, когда `Cover` | проход по `WoodyStore.HighWater` + сортировка по Id в чанке; на стороне рендера 50 тыс. растений — 12–14 мс суммарно, растянуто бюджетом 3 мс/кадр (`FloraRenderSettings.ApplyBudgetMs`) |
| Поля трав и полога | раз в игровой час — строки чанков `CaptureFields(row, row+1)` по очереди (24 часа × N строк) или раз в сутки целиком | 256² ячеек × 4 слота |
| Условия кадра | каждый кадр (`UpdateEnvironment`) | несколько чтений |

На ×8 сутки длятся 90 с реального времени — обновление раз в сутки достаточно для роста; облиственность меняется на ±0,35 в сутки (фенология ядра), т. е. весной и осенью почти все лиственные чанки меняются каждые сутки — это ожидаемо и укладывается в бюджет применения.

### 4.4. Новые и погибшие растения

- Новое растение (всход ≥ 0,25 м) попадает в чанк при следующем снимке; рендер получает чанк целиком. Всходы ниже 0,25 м не рисуются (их скрывает травостой).
- Погибшее растение просто отсутствует в новом снимке чанка. Освобождённый индекс `WoodyStore` с новым поколением даёт **новый** `Id` → у нового растения другой вариант модели и поворот; «перескоков» формы у живых растений нет.
- Чанк, в котором не осталось растений, приходит пустым (`Count = 0`).

### 4.5. Инициализация нового мира

1. После создания/загрузки `Simulation` (и после подготовки Wildlands — этап 2.5): `new SimFloraSnapshotSource(sim.World)`, затем `CaptureAll()`.
2. `new FloraRenderer(assets, source.Catalog, new FloraGrid(geo.N, geo.CellSize), terrain, settings)` — один раз на мир (строит модели и атлас импосторов: 0,65–0,9 с, см. отчёт); `SetSource(source)`.
3. Первый `Update` получает `Full`; применение растягивается на несколько кадров. Для Wildlands M (0,5–0,85 млн древесных, `PROJECT_CONTEXT.md` риск 18) полную загрузку лучше выполнить за экраном подготовки — вызывать `Chunks.Step` с большим бюджетом до `!Chunks.Busy`.
4. Смена мира: новый `WorldId` → полный сброс; объект рендера можно не пересоздавать, если сетка та же.

### 4.6. Травяной покров

Трава строится **только** из поля `Herbs` (нет биомассы — нет пучков): пучков на м² = min(предел вида, граммы / граммов на пучок) × густота качества. Места пучков — хеш (ячейка, вид, номер): пучок k всегда на одном месте, при росте биомассы добавляются новые. Поле зелени и ветоши задаёт сухую/зимнюю траву, `Canopy.R` — затенение под пологом, `Surface` — снег и намокание. Поля загружаются в глобальные текстуры `_FloraHerbA/_FloraHerbB/_FloraHerbCell/_FloraCanopy/_FloraSurface` и `_FloraFieldParams` — их может читать материал рельефа.

### 4.7. Смена сезона

Рендер не считает климат. Из `YearPhase` `FloraSeasonController` получает только палитру: свежесть весенней листвы, ход осенней окраски (каждая карточка листвы меняет цвет в свой момент), окна цветения и плодов видов, увядание трав. **Сколько листьев на дереве — решает симуляция** (`Leaf` растения): карточки листвы исчезают по своему случайному числу при уменьшении облиственности; у хвойных облиственность 1. Снег на кронах и траве — из `Surface`/`Snow`.

### 4.8. Освещение

Растительность освещается главным светом URP (`RenderSettings.sun`/главный направленный свет) с каскадными тенями и амбиентом (`SampleSH`, т. е. `RenderSettings.ambientProbe`), туманом сцены (`MixFog`) и SSAO рендерера (проходы `DepthNormals` есть у всех шейдеров). Освещение мира задаёт `WorldView`/`WorldApp` — рендер флоры ничего не меняет в источниках света. Требования: главный свет — направленный с тенями; амбиент — актуальный SH (при `AmbientMode.Skybox` — `DynamicGI.UpdateEnvironment()` после смены неба).

## 5. Что должен предоставить SimHost

| Что | Зачем |
|---|---|
| Точку вызова «после суточного шага флоры» (или флаг `FloraDayCompleted`) | `CaptureWoody()` и публикация раз в сутки |
| Точку вызова «после часового шага» | `CaptureFields(row…)` по строкам чанков |
| Доступ только на чтение к `World` между шагами (уже есть: главный поток) | адаптер читает массивы без копирования |
| Средний снег мира или поле снега, интенсивность дождя | `UpdateEnvironment(snow, rain)` |
| Высоты рельефа (`Geo.Terrain`, шаг 2 м) | `FloraTerrain` для посадки растений; лучше передать массив высот, а не пересчитывать |

Когда появится отдельный поток симуляции: `Stage*/Commit` вызывать из него (издатель потокобезопасен), `TryGetUpdate` остаётся на главном потоке.

## 7. Изменения в общих файлах при интеграции (НЕ выполнены в этой ветке)

1. **`Worldbound.Runtime.asmdef`**: добавить ссылки `Worldbound.FloraView`, `Worldbound.FloraView.Contract`, `Worldbound.FloraView.SimAdapter` (сборки модуля не `autoReferenced`).
2. **`WorldApp.cs`**:
   - при открытии мира: создать `FloraTerrain` из `Geo`, `SimFloraSnapshotSource`, `FloraRenderer` (ассет `FloraRenderAssets` — через поле сцены или `Resources`);

   - пресеты качества игры → `FloraRenderSettings.For(...)`;

3. **`WorldView.cs` / материал `WorldTerrain`**: читать глобальные поля флоры (`_FloraCanopy`, `_FloraHerbA/B`, `_FloraHerbCell`, `_FloraSurface`) для цвета травостоя и лесного массива вдали — как это делает `Stand/StandGround.shader`; сейчас рельеф красится индексом зелени (этап 2.8 — слой биомов и покрова).
4. **Сборка**: сцена `Main.unity` создаётся `BuildTools.Setup`; ассет `FloraRenderAssets` должен попасть в сборку (ссылка из компонента сцены или `Resources`).
5. **Сохранения**: не меняются — рендер ничего не сохраняет.

## 8. Ограничения контракта и открытые вопросы

- Отображения «высота травостоя», «ветошь», «влажность поверхности» в ядре сейчас отсутствуют; адаптер даёт приближения, рендер работает и с нулями.
- Полная пересылка мира M с 0,5–0,85 млн растений (весна/осень) — около 10–20 кадров применения при бюджете 3 мс; оценка, на мире M не измерялась.
- Номера видов совпадают с каталогом (`PlantCatalog`); визуальный профиль — по ключу. Новые виды каталога без своего профиля получают общий.
- Контракт версии 1 (`FloraContract.Version`); при несовместимом изменении полей — повысить версию.
